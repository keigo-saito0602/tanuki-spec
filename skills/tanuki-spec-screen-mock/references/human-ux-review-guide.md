# 画面モックの人手・支援技術・UX評価手順

`scripts/validate_screen_mock.py`（T-22A、静的な構造検査）と
`scripts/check_browser_contract.py`（T-22B、実ブラウザでの実測）は、どちらも
「手掛かりが存在するか」「寸法が足りているか」という**構造・数値**しか判定できない。
色以外の手掛かり（文字・境界線・アイコン）が**実際に見分けの手段として機能するか**は、
最終的に人の判断が要る。この手順書はその人手評価をカバーする。

## 対象と前提

- 対象: `render_screen_mock.py`が生成したHTML（`<phase>/views/画面モック.html`）
- 前提: T-22A・T-22Bの機械検査を通過していること。まずそちらでエラーを解消してから、この手順に進む
- 配色の判断（3節）はデザインモードで行う。ワイヤーモードは配色を無効化した構造確認専用のため対象外
- macOSでの実施を想定する。VoiceOverは`⌘（Command）+ F5`で起動・終了する

## 1. キーボード操作の確認

マウス・トラックパッドを使わず、Tabキー（戻る場合はShift+Tab）とEnterキーだけで操作する。

1. ヘッダーのモード切替、サイドバーの画面一覧、各画面内の見出し・リンク・ボタン・遷移リンクを、
   Tabキーだけで一通り辿れることを確認する。
2. タブ移動の順序が、画面上の視覚的な並び（上から下、左から右）と一致しているか確認する。
   ずれている場合は`[要確認]`として記録する。
3. Enterキーでリンク・ボタンがクリックと同じ動作（画面遷移、モード切替）をするか確認する。
4. 今どこにフォーカスがあるか、太さのある外枠で常に視認できるか確認する
   （基準は[`uiux-principles.md`のフォーカス表現節](./uiux-principles.md#フォーカス表現)）。
5. キーボード操作だけで行き止まり（フォーカスが特定要素から抜け出せない、
   同じ場所を無限に回る）がないか確認する。

## 2. 支援技術（スクリーンリーダー）の確認

VoiceOverなど、実際にスクリーンリーダーを起動して確認する（自動化された文字列チェックでは代替できない）。

1. 見出し単位のジャンプ（VoiceOverは`Ctrl+Option+Cmd+H`）で、`h1`→`h2`→…の順に
   画面構造を過不足なく辿れるか確認する。
2. 各画面の目的（`purpose`）が読み上げで伝わるか確認する。
3. 状態表示ブロックへフォーカスしたとき、色に頼らず意味が読み上げで伝わるか確認する。
   [`mock-html-contract.md`の非色覚手掛かり表](./mock-html-contract.md#状態表現部品のマーク契約data-state)
   と照らして、次を1つずつ確認する。
   - `empty-state`: 見出し「データがありません」とメッセージが読み上げられる
   - `alert`（`error`）: 種別文言「エラー」とメッセージが読み上げられる
   - `alert`（`forbidden`）: 種別文言「権限がありません」とメッセージが読み上げられる
   - `loading`: 「読み込み中」の文言が読み上げられる（`aria-live="polite"`）
4. 記号アイコン（`aria-hidden="true"`）が、隣接する文言と重複して読み上げられていないか確認する
   （アイコンは装飾扱いであり、意味は文言側が持つ設計）。
5. 表のキャプション（「この画面の5状態」「遷移元・操作・遷移先の一覧」等）が読み上げられるか確認する。

## 3. UX観点: 色以外の手掛かりの意味判断

T-22Aが確認するのは「`data-state`を持つ要素に文字・境界線・アイコンのいずれかがある」という
**構造の有無**だけである。ここでは、その手掛かりが**実際に見分けの手段として機能するか**を判断する。

1. ブラウザの開発者ツールで色覚特性のエミュレーションを有効にする
   （Chrome DevTools: 検証ツールを開き `⌘+Shift+P` →「Show Rendering」→
   「Emulate vision deficiencies」でグレースケール・色覚タイプごとに切り替える）。
   devtoolsが使えない場合は、macOSの「システム設定 > アクセシビリティ > 画面表示 >
   色フィルタ」で代替する。
2. デザインモードで、同一画面または近い配置にある`alert`の`error`状態と`forbidden`状態を見比べる。
   色を除いた状態で、境界線の太さ・線種、アイコンの形、文言だけで2つを区別できるか判断する。
3. 同様に、`empty-state`と`loading`が、色なしで見分けられるか判断する。
4. 区別できない、または見分けに時間がかかる場合は、次のいずれかを強める提案を
   `screens.yaml`の該当ブロックの`notes`へ`[要確認: 提案内容]`として記録する。
   この手順書自体でHTML/CSSを直接修正しない。
   - 境界線の太さ・線種の差を広げる
   - アイコンの形状差を広げる（似た記号を避ける）
   - 文言の差を広げる（同じ語幹を避ける）

## 4. 実施記録

実施のたびに、次の記録を`<phase>/reports/`配下（例:
`<phase>/reports/02_画面モックUX評価.md`）へ残す。記録がなければ「実施した」とみなさない。

```yaml
mock_ux_review:
  date: "YYYY-MM-DD"
  target_html: "<phase>/views/画面モック.html"
  reviewer: "<担当者>"
  keyboard: {tab_order_ok: true, focus_visible_ok: true, no_trap: true}
  screen_reader: {tool: "VoiceOver", headings_ok: true, state_announced_ok: true}
  non_color_cue_distinguishable: {error_vs_forbidden: true, empty_vs_loading: true}
  issues: []   # 見つかった問題を1件1行で。無ければ空配列
```

## 判定

1〜3のすべてで未消化・未確認の項目がなく、`issues`が空であれば「人手評価OK」とする。
`issues`がある場合は該当項目を`screens.yaml`の`notes`へ`[要確認]`として転記し、
修正または合意の上で再実施する。
