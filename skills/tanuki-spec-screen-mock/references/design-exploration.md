# 画面モックのデザイン探索

画面モックは、要件を部品の組み合わせへ置き換える作業ではない。利用者が実際の業務で何を判断し、どこで迷い、失敗したときにどう復旧するかを、実装前に検証するための仮説である。

## 調査の順序

画面を洗い出す前に、次の順で確認する。確認できなかったものは推測で埋めず、`notes`またはプロジェクトの調査記録へ未確定事項として残す。

1. **利用者**：誰が、どの頻度で、どの端末・環境から使うか。経験差、権限差、代理操作の有無も確認する。
2. **業務**：画面を開く前のきっかけ、達成したい判断、後続の作業、失敗時の復旧先を確認する。
3. **既存UI**：同じ利用者が触る既存画面、ナビゲーション、用語、入力順、状態表現を確認する。既存画面と異なる理由がなければ、学習済みのパターンを引き継ぐ。
4. **ブランド**：ロゴ、色、文字、余白、写真・イラストの扱いを確認する。ブランドは装飾だけでなく、信頼感や行動の優先順位にどう作用するかを見る。
5. **制約**：認証、権限、通信、データ量、端末幅、アクセシビリティ、運用上の締切を確認する。

調査結果は少なくとも次の3種類に分ける。

| 種類 | 意味 | 画面定義での扱い |
| --- | --- | --- |
| 事実 | コード、既存画面、利用者への確認などで確かめたこと | `rationale`の根拠にする |
| 仮説 | まだ確認していないが、検証するために置く考え | `hypothesis`に書く |
| 未確定 | 判断に必要な情報が不足していること | `notes`へ`[要確認: 質問]`として残す |

## 画面ごとの探索カード

各画面に次の項目を置き、「この画面を作ること」ではなく「この問いに答えること」をレビューの単位にする。

| 項目 | 書く内容 | 例 |
| --- | --- | --- |
| `design_question` | レビューで決めたい問いを1つ、必要なら補助問いを続ける | 初めての生徒が空き枠を比較して予約へ進めるか |
| `hypothesis` | 現時点で最も妥当と思う利用者行動・情報順序 | 日付を先に選べば候補を絞り込める |
| `risk` | 判断を誤ったときの影響と不確実性を合わせた`low`/`medium`/`high` | medium |
| `validation_task` | モックを見た人が行う具体的な課題。感想ではなく観察できる行動にする | 「明日の午後に空き枠を探し、最初に押す場所を説明してください」 |
| `rationale` | 採用した情報構造・導線・既存UIとの関係。事実と推論を分ける | 既存予約画面と同じ日付フィルタを先頭に置く |

`validation_task`は「分かりやすいですか？」のような抽象的な質問にしない。利用者に目的を与え、どこを見て何を押すかを説明してもらう。これにより、見た目への好みではなく、情報の優先順位と導線を検証できる。

## 代替案の比較

案を増やすこと自体を成果にしない。`exploration_mode`は判断の不確実性に応じて選ぶ。

- `compare`：新しい導線、既存UIからの大きな変更、または`risk: high`の画面。`alternatives`に判断を変えうる2〜3案を並べる。
- `inherit`：同じ利用者・業務・制約で有効な既存パターンが確認できる低・中リスク画面。`inherited_from`に継承元を示し、採用案1件だけを書く。

どちらも1案だけを`decision: adopted`にする。`compare`の残りは`decision: rejected`とし、採用・却下それぞれの理由を`reason`へ書く。

```yaml
exploration_mode: compare
alternatives:
  - id: alt-filter-first
    name: 条件を先に絞る
    summary: 日付と講師を先頭に置く
    decision: adopted
    reason: 初回利用でも候補数を減らしやすく、既存画面の順序とも一致するため
  - id: alt-calendar
    name: カレンダー中心
    summary: 月間カレンダーから日付を選ぶ
    decision: rejected
    reason: 週単位の空き枠比較が主目的で、月間表示は情報密度が高くなるため
```

比較する場合は、異なる情報構造、導線、状態の扱いなど、判断を変えうる案を扱う。継承する場合も、既存パターンが今回の利用者と業務に適合する理由を確認する。採用理由には、利用者・業務・既存UI・技術制約のどれを優先したかと、残るトレードオフを書く。

## リスクに応じた状態設計

`states`には、比較可能な最低限として通常・空・読込中・エラー・権限なしの5状態を残す。ただし、5状態を同じ詳しさで実装・説明する必要はない。

`state_strategy.priority_states`で、その画面のリスクに応じてレビューを重点化する状態を示す。`state_strategy.rationale`には、なぜその状態を優先するかを書く。

```yaml
risk: high
state_strategy:
  priority_states: [normal, error, forbidden]
  rationale: 予約確定の失敗と権限切れで、二重予約や作業のやり直しが起きるため
```

業務固有の状態を5状態の語彙へ無理に押し込めない。期限切れ、下書き、二重送信、承認待ちなどは、`notes`または`state_strategy.rationale`に具体的な表示・復旧方法とともに書く。追加状態を共通カタログやゲートの固定語彙へ増やすのは、複数案件で再利用する必要が確認できたときだけにする。

## 既存UI・ブランドとの差分

既存画面を参照した場合、単に「踏襲」と書かず、次を記録する。

- 何を踏襲したか（ナビ、用語、入力順、状態表現など）
- 何を変えたか
- 変える必要がある業務上・利用者上の理由
- 差分を誰に、どの操作で検証するか

参考ソースがスクリーンショットやURLだけの場合は、観測した見た目と推測した意図を分ける。色の確度は`design-token-extraction.md`の規則に従い、URLから推測した値を確定扱いにしない。
