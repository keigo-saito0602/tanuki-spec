# 要件からデザインを起こす判断規範

要件定義書には「何ができるか」しか書かれていない。そこから画面を起こすときの判断基準。

## 画面ごとに必ず検討する5状態

レビューで最も抜けるのがここ。`screens.yaml` の `states` で必須にしている。

| 状態 | 検討内容 |
| --- | --- |
| 通常 | データがある平常時 |
| 空 | 0件のときの案内と、次に取れる行動 |
| 読込中 | 待たせる場合の表示 |
| エラー | 失敗理由と復旧手段 |
| 権限なし | 見えない／押せない場合の扱い |

## 情報設計と導線

- 1画面1目的。目的が2つあるなら画面を分ける
- プライマリボタンは1画面に1つ。並列に強調すると、どれを押せばよいか分からなくなる
- 現在地が常に分かる（パンくず・ステップ表示）
- どの画面からも戻れる。行き止まりを作らない。意図的な終端は `terminal: true` で明示する
- 主要タスクは3クリック以内

## フォーム

- ラベルは項目の上に置く。左に置くと折り返しで対応が崩れる
- 必須は色でなく文字で明示する。色だけでは色覚特性によって伝わらない
- エラーは項目の直下に出す。画面上部にまとめると、どの項目か分からない
- 入力欄の幅を想定文字数に合わせる。郵便番号に長い欄を置かない

## モバイル

- タップ対象は44px以上、隣接する対象を密集させない
- 1カラムにする
- 主要CTAは固定フッターに置く

## 配色

[`../../../tanuki-spec-all/references/color-design.md`](../../../tanuki-spec-all/references/color-design.md)
の役割トークンとコントラスト基準に従う。本ファイルに配色規範を重複して書かない。

参考ソースが無い場合の既定トークンは
[`../templates/design-tokens-template.json`](../templates/design-tokens-template.json) を使い、
すべて `confidence: proposed` として提案であることを示す。

## デザイントークンの階層

`design-tokens.json`は2階層。**1階層目はグループ**（`color`・`typography`・`spacing`・`radius`・`shadow`。`tokens.py`の`VALUE_GROUPS`が正本）、**2階層目はグループ内の役割名**（例: `color.primary`、`typography.size_base`）。役割名は`color`の5つ（`primary`/`surface`/`text`/`line`/`accent`）以外は自由に追加できる。`tokens.py`の`to_css_variables()`は各グループの中身をそのまま`--<グループ>-<役割名>`というCSSカスタムプロパティへ機械的に変換するため、**新しい役割名を追加するだけでコード変更なしに尺度を増やせる**。

原始値（生のhex・px数値）を`screens.yaml`やブロック定義へ直接書かず、必ず役割名を経由する。値を1箇所（`design-tokens.json`）で直せば、参照している全ブロックへ反映される。他の設計トークン体系にあるような「primitive→semantic」の中間層は持たない。値は役割名に直接入る、この2階層だけの単純な構造にしている（決定論的な生成という本スキルの方針に合わせている）。

## タイポグラフィ尺度

`typography`グループは現状`font_family`と`size_base`だけを既定で持つ。複数の見出しレベルを扱う画面では、次の役割名を追加する（すべて`confidence: proposed`の既定値。実測できたら`confirmed`へ上げる）。

| 役割名 | 既定値 | 用途 |
| --- | --- | --- |
| `size_xs` | `12px` | 補足文、キャプション |
| `size_sm` | `14px` | 表内文字、フォームのヒント |
| `size_base` | `16px`（既存） | 本文 |
| `size_lg` | `20px` | 小見出し |
| `size_xl` | `24px` | 画面タイトル |
| `size_2xl` | `32px` | 一覧のゼロ件時など、強い訴求が要る箇所限定 |

1段飛ばしを基本にする（`size_base`の次は`size_lg`）。同じ画面で3段階を超える見出しレベルを使わない。見出しレベルを飛ばす（`h1`の次に`h3`が来る等）とスクリーンリーダーの利用者が構造を誤解するため、視覚的な尺度と見出しタグの順序を一致させる。

## 余白尺度

`spacing`グループは現状`unit`（8px）だけを持つ。8pxを基準単位とする8点グリッドで、次の役割名を追加する。

| 役割名 | 既定値 | 用途 |
| --- | --- | --- |
| `xs` | `4px` | アイコンと文字の間など、同一要素内の詰め |
| `sm` | `8px`（既存`unit`相当） | 関連する項目同士の間隔 |
| `md` | `16px` | ブロック内の要素間 |
| `lg` | `24px` | ブロックとブロックの間 |
| `xl` | `32px` | セクションの区切り |
| `2xl` | `48px` | 画面の主要な区画の区切り |

`xs`未満の余白（境界が触れ合う状態）は作らない。関連性が高いほど狭い段階、関連性が低いほど広い段階を使う。同じ意味の間隔（例: ブロック内の要素間）で異なる段階を混在させない。

## 操作状態

現在の`assets/screen-mock.html`は`:hover`・`:focus`・`:disabled`・`:active`のスタイルを持たない（静的なワイヤー/デザイン切替のみ）。この節は、将来これらを実装する・または実装先（本番UI）へ引き継ぐときの判断基準を示す。screens.yamlの`notes`に、対象ブロックの操作状態を明記して残す。

- **ホバー**: 背景・境界線のいずれかを変える。文字色だけの変更は、色を見分けられない場合に伝わらない。
- **フォーカス**: 「フォーカス表現」節を参照。最優先で実装する状態（キーボード操作の唯一の手掛かり）。
- **選択中**: 背景変更に加え、選択を示す文字・アイコン（チェックマーク等）を併用する。背景色だけでは色覚特性によって伝わらない。
- **無効化（disabled）**: 操作できないことを、コントラストを下げるだけでなく`title`属性やヘルプ文で理由を示す。理由が示せない無効化ボタンは、そもそも画面に出さない方が良いことが多い（押せない理由が分からないボタンはユーザを迷わせる）。
- **読込中の個別要素**（画面全体のローディング状態とは別）: ボタンを押した直後などは、ボタン自体の文言を「送信中…」に変え、二重送信を防ぐ。

## フォーカス表現

- フォーカスは色の変更だけにせず、太さのある外枠（アウトライン）を表示する。`outline: none`を、代替のフォーカス表現なしに使わない。
- フォーカスの外枠は背景・要素本体のどちらともコントラスト`3:1`以上を確保する。
- タブ移動の順序は、画面上の視覚的な並び（上から下、左から右）と一致させる。`tabindex`に正の値を使わない。
- キーボードだけで、画面内のすべての操作（遷移・フォーム入力・送信）が完結できることを判断基準にする。マウス・タップ操作しか前提にしていない部品を作らない。

根拠:

- [Focus Appearance — WCAG 2.2](https://www.w3.org/TR/WCAG22/#focus-appearance)（確認日: 2026-08-12）
- [Focus Not Obscured — WCAG 2.2](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum)（確認日: 2026-08-12）

## 生成UIの品質ヒューリスティクス

AIが機械的に生成した画面によく出る欠陥を、レビュー観点として先回りして挙げる。

- **同じ余白・角丸・文字サイズを繰り返す。** 画面ごと・ブロックごとに微妙に異なる値を使わない（尺度から外れた値が1つでもあれば、他はすべて機械的に生成されたのに、その1つだけ手直しされたように見え、信頼性を損なう）。
- **プレースホルダー文言を本物らしく見せすぎない。** `<画面名>`のような未確定を示す記法（本スキルの既存規約）を、内容が確定したかのような具体的な仮の文言（「サンプル太郎」等）に置き換えない。人が見て「これは埋めるべき場所だ」と即座に分かる状態を保つ。
- **情報密度を画面内で揃える。** 1つのブロックだけ極端に情報量が多い、または少ない画面は、要件の分解が粗いサインである。ブロック単位で情報量の偏りがないか確認する。
- **同じ役割の部品には同じ見た目を使う。** 同じ「保存」の意味を持つボタンが画面によって色・位置・文言が違うと、学習した操作パターンが使えなくなる。
- **本文と装飾を区別できる密度にする。** 枠線・背景色・アイコンを装飾のためだけに増やさない。装飾が増えるほど、本当に注意すべき箇所（エラー、警告）が埋もれる。

根拠:

- [Consistency and standards — Nielsen Norman Group](https://www.nngroup.com/articles/ten-usability-heuristics/)（確認日: 2026-08-12）
- [Aesthetic and minimalist design — Nielsen Norman Group](https://www.nngroup.com/articles/ten-usability-heuristics/)（確認日: 2026-08-12）

## 忠実度の使い分け

モックHTMLはワイヤーとデザインの2モードを持つ。**まずワイヤーモードで構成と遷移を確認してもらう**。
見た目が作り込まれていると、レビューが余白やボタンの色の議論へ流れ、導線の問題が未解決のまま残る。
色の確認はデザインモードへ切り替えて別に行う。
