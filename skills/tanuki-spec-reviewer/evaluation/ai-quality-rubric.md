# AI品質評価 運用方法（生成AI活用開発の品質管理観点を「評価できる運用」に落とす）

このドキュメントは、`spec-items.yaml` の `ai_quality_perspectives`（生成AI品質管理20観点）を、
本SKILLの「ユーザーストーリー → 穴埋め生成 → カバレッジ評価」フローの中で**実際に評価・記録できる運用**へ落とし込んだもの。

- 対象: ユーザ（個人開発。Claude Code＝設計/レビュー、Codex＝実装の分業）
- 出典元: `spec-items.yaml` のAI品質20観点＋Web調査（[`research/web-sources.md`](../research/web-sources.md)）

---

## 0. 採用方針：案B（標準）

Web調査の結論として、個人開発規模では大企業QMS（IEEE/DO-178C等）は過大。
**「軸別YES/NOチェックリスト ＋ 一方向トレース ＋ 前回との差分検知 ＋ 低頻度の人手サンプリング」** が最もバランスが良い（案B）。

採用の根拠（要点と出典）:
- スキルの評価は、発火精度・単独動作・既存スキルとの共存・出力品質に分ける。各更新で代表ケースを再実行する。
- 決定論で判定できる項目（SSOT整合、マーカー、未記入、根拠記載）はスクリプトで検証し、モデル判断が必要な6軸だけを別担当が採点する。
- ルーブリックは総合点にせず、判断不可を許す。採点者・モデル・対象仕様書のSHA-256を記録し、レビューの改ざん・取り違えを検知する。
- 詳細な出典と取得日は[`research/web-sources.md`](../research/web-sources.md)を参照する。

## 1. 運用フロー全体（5ステージ）

```
[入力] ざっくりユーザーストーリー
   │
   ├─ ①入力ゲート（INVEST 6軸チェック）……… Story品質が低ければ受入基準の追記を促す
   │
   ├─ ②穴埋め生成（根拠明記ルール）………… 過去仕様を参照し各項目を生成。埋められない項目は空欄＋[要確認]
   │
   ├─ ③カバレッジ評価（coverage.py）………… 必須充足率・欠落リスト（機械判定・決定論的）
   │
   ├─ ④AI品質ルーブリック（6軸・別セッション採点）… 完全性/曖昧性/整合性/トレース/実装可能性/根拠
   │
   └─ ⑤人手サンプリング＆差分（低頻度）……… 月1回ユーザが数件確認＋前回との差分レビュー
   │
[出力] Codexへ引き渡してよい状態（DoD）判定
```

- ①③は自動・軽量、②④はAIが規則に沿って実行、⑤のみ人手（低頻度）。
- ③は**決定論的**（`coverage.py`）、④は**AI判定**（ルーブリック）と役割を分離する。

---

## 2. ステージ別チェック項目

### ①入力ゲート — ユーザーストーリーの INVEST 6軸（YES/NO）

生成を始める前にストーリー自体の品質を担保する（インプット品質の確保）。

- [ ] **I**ndependent: 他ストーリーと独立して着手できるか
- [ ] **N**egotiable: 実装詳細を固定しすぎていないか（What中心か）
- [ ] **V**aluable: 誰にどんな価値があるか明確か
- [ ] **E**stimable: 規模を見積もれるだけの情報があるか
- [ ] **S**mall: 1機能単位に十分小さいか
- [ ] **T**estable: 受入基準（合否条件）を書けるか

→ **Testable が NO** のときは、生成前に受入基準の補足をユーザーに求める（曖昧なまま生成しない）。

### ②穴埋め生成 — ハルシネーション対策ルール（必須）

- 各FILLブロックに`**根拠**: [入力] ...`または`**根拠**: [参照] <path>#<heading>`を記録する。内部の思考過程は出力しない。
- 参照元に根拠が無い項目は**勝手に埋めない**。空欄のまま `[要確認: 根拠なし]` フラグを残す。
- 参照仕様（過去案件）を使う場合、その**出典（リポジトリ/ファイル）を項目脚注に明記**する。
- 断定できないものは「（推定）」と明示する。

### ③カバレッジ評価 — 決定論チェック（`coverage.py`）

- 必須充足率・全体充足率・欠落項目リストを出力（YES/NO＝充足/未充足）。
- **絶対%を合否基準にしない**。用途は「必須の欠落ゼロ」の確認と、前回との差分把握。
- `[要確認]` フラグの数も併記し、多い場合は②へ差し戻す。`spec_gate.py`で根拠未記載も含めて検証する。

### ④AI品質ルーブリック — 6軸（別セッション/別担当が採点）

各軸を **PASS / 要改善 / 判断不可** の3値で判定（総合1点にしない）。採点は生成に使ったセッションと**別セッション**で行う（自己優遇バイアス回避）。

| 軸 | 判定基準（YES/NOで確認） | 主に対応するAI観点(id) |
| --- | --- | --- |
| 完全性 | 必須項目がすべて実質記入され、`[要確認]`が残っていないか | aiq-hallucination, aiq-coding-cover |
| 曖昧性の排除 | 一文一意か／「適切に」「等」等の曖昧語や未解決TBDが無いか | aiq-input-quality, aiq-prompt-fact |
| 整合性 | 項目間・他成果物（要件↔設計↔受入基準）で矛盾が無いか | aiq-design-test-view, aiq-cross-review |
| トレーサビリティ | 各要件が設計セクション/受入基準へ1方向リンクで辿れるか | aiq-qa-story |
| 実装可能性 | 受入基準がテスト可能で、制約・非機能と衝突しないか | aiq-test-cover |
| 根拠・非ハルシネーション | 各項目に根拠/出典/前提が示され、捏造が無いか | aiq-human-review, aiq-prompt-mgmt |

- **順序バイアス対策**: 項目数が多い工程は、採点時に項目の並びをシャッフルして2回判定し、食い違う項目だけ人手確認。
- **判断不可** は無理に PASS/要改善にせず、そのまま⑤の人手確認へ回す。

### ⑤人手サンプリング＆差分（低頻度・月1目安）

- ユーザが**数件だけ**サンプルを開き、④のAI判定と自分の判定がズレていないかを確認（ルーブリック校正）。
- 前回生成との**差分（追加/削除/変更された項目）**をレビューし、退行が無いかを見る。
- 良かった点/悪かった点を `references/` のナレッジに追記（横展開）。

### 出力ゲート — DoD（Codexに渡してよいか）

- [ ] 必須充足率100%（欠落ゼロ）
- [ ] `[要確認]`フラグが残っていない（または残件がユーザ確認済み）
- [ ] ④6軸に「要改善」が残っていない
- [ ] 受入基準がテスト可能な形で書かれている

## 3. 20観点 → 運用マッピング（すべての観点がどこかで評価される）

`spec-items.yaml` の20観点を、上記フローのどこで担保・評価するかの対応表。**「観点が運用のどこにも紐づかない」状態を作らない**のが目的。

| 観点(id) | 名称 | 担保する場所 |
| --- | --- | --- |
| aiq-risk-typing | 生成AI特有リスクの類型化 | 本ドキュメント §0（前提として明示） |
| aiq-human-review | 成果物の人間レビュー原則 | ⑤人手サンプリング／出力ゲート |
| aiq-poc | PoCによる品質影響の事前検証 | 初回導入時にE2Eサンプルで検証（examples/） |
| aiq-input-quality | インプット品質の確保 | ①INVEST入力ゲート |
| aiq-prompt-mgmt | プロンプトの管理・改善 | SKILL.md/テンプレをGit管理＋④根拠軸 |
| aiq-knowledge | ナレッジの蓄積と横展開 | ⑤良否をreferences/へ追記 |
| aiq-plan-extra | 追加作業を見込んだ計画 | ②`[要確認]`の差し戻しを工数に織り込む |
| aiq-qa-story | 品質保証ストーリーへの反映 | ④トレーサビリティ軸 |
| aiq-qc-plan | 品質管理計画への考慮点追加 | ③カバレッジ＋④ルーブリックの記録 |
| aiq-design-test-view | 設計観点・テスト観点の追加 | ④整合性軸／spec-items.yamlの観点更新 |
| aiq-quant-qual | 定量・定性の両面評価 | ③定量(%)＋④定性(6軸) |
| aiq-hallucination | ハルシネーション・整合性確認 | ②根拠明記ルール／④完全性軸 |
| aiq-cross-review | 生成AIレビューの見落とし対策 | ④別セッション採点／⑤人手 |
| aiq-coding-cover | コーディング規約・条件網羅性 | 実装フェーズ（Codex）へ引き渡し時のDoD |
| aiq-test-cover | テスト資材の網羅性・妥当性 | ④実装可能性軸（受入基準のテスト可能性） |
| aiq-prompt-fact | プロンプトのレビュー観点 | ②「わからないと言わせる」ルール |
| aiq-quality-level | 品質水準の設定方法 | 出力ゲートのしきい値（必須100%等） |
| aiq-poc-metrics | PoCの定量・定性評価項目 | examples/のE2Eで充足率・安定性を確認 |
| aiq-case-feedback | プロジェクト事例の反映 | ⑤ナレッジ追記→spec-items.yamlへ反映 |
| aiq-role-split | 生成AI活用の作業配分見直し | 本フロー全体（AI=生成/判定、人=最終判定） |

## 4. 評価結果の記録フォーマット（`examples/` に実サンプルあり）

1回の生成ごとに、次のブロックをサイドカーファイルに残す。`generated_spec_sha256`は対象MarkdownのSHA-256、`reviewer.independent`は生成担当と別セッション/別担当であることを示す。保存後に`validate_review.py`で検証する。

```yaml
ai_quality_review:
  date: 2026-07-14
  target: requirements   # 工程
  reviewer: {role: reviewer, model: "モデル名", independent: true}
  generated_spec_sha256: "対象MarkdownのSHA-256"
  input_gate_invest: {I: yes, N: yes, V: yes, E: yes, S: yes, T: yes}
  coverage: {required_coverage: 100.0, overall_coverage: 88.0, todo_flags: 0}
  rubric:                # PASS / 要改善 / 判断不可
    完全性: PASS
    曖昧性の排除: PASS
    整合性: 要改善        # 例：受入基準と非機能要件が一部矛盾
    トレーサビリティ: PASS
    実装可能性: PASS
    根拠_非ハルシネーション: PASS
  human_sampling: {reviewed: false, note: 次回月次で確認}
  dod_passed: false      # 整合性が要改善のため未通過
  diff_from_prev: 初回のため無し
```
