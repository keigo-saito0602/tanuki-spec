# tanuki-spec 品質原則

tanuki-specは、テンプレートの充足ではなく、案件に適した判断と読者の理解を最適化する。機械ゲートは品質の下限であり、十分条件ではない。

## 優先順位

1. 利用者・業務課題・プロジェクト固有の制約を理解する。
2. 重要な判断について、根拠・代替案・トレードオフを残す。
3. リスクと不確実性に応じて要件・設計・テストの深さを変える。
4. 読者が判断する順序へ人向け成果物を再編集する。
5. ID・網羅性・トレーサビリティを機械的に保証する。

## 生成前の理解

次を確認してから要件や設計を書く。

- cc-sddの`brief.md`・`roadmap.md`と`.kiro/steering/`
- プロジェクトの目的、対象利用者、業務フロー、用語
- 既存コード、画面、データ、外部連携、運用制約
- 今回のスコープ、対象外、責任境界、依存関係
- 事実、推測、未確定事項の区別

情報が不足していてもテンプレートを推測で埋めない。判断に必要な不足だけを質問し、回答待ちでも進められる部分は根拠を付けて進める。

## リスクベースの深掘り

各要件を、利用者・事業への影響、不確実性、技術的な結合、失敗時の復旧難度で`low`・`medium`・`high`に分類する。

- `low`: 目的、受け入れ条件、根拠を簡潔に示す。
- `medium`: 正常系に加え、主要な例外、権限、データ影響、検証方法を示す。
- `high`: 現在の問題、根拠、前提、通常・代替・失敗・復旧、状態遷移、境界、監査、代替案、未決事項、検証方法まで掘る。

全要件を同じ厚さにしない。図・表も、読者の判断に役立つ場合だけ作る。

## 調査と設計判断

設計前に`research.md`または案件の調査記録へ次を残す。

- 調査した問いと情報源
- 既存実装から確認できた事実
- 比較した案と採用しなかった理由、または継承した既存パターンと今回も適合する理由
- 採用案、理由、トレードオフ
- 前提が変わったときの再検討条件

人向け設計書には調査全文を貼らず、採用判断と重要な根拠だけを残す。

## 正本と人向け成果物

Markdown・YAMLの正本は監査・再生成・トレーサビリティのために保持する。閲覧用HTMLは正本の単純連結にせず、資料ごとの目的へ編集する。

要件定義書・設計書・テスト項目書の読者向け本文は、概要ではなく、その本文だけで判断できる内容にする。監査付録にだけ詳しい要件や設計を置かない。監査付録は根拠、対象の本文見出し、要件・設計・テストIDを結ぶ索引であり、本文の複製場所ではない。

| 成果物 | 読者が判断すること |
| --- | --- |
| サマリ | 何を作るか、何が未決か、最大のリスクは何か |
| 要件定義書 | 誰のどの問題を、どの条件で解決するか |
| 設計書 | なぜこの方式か、境界・データ・処理・失敗時はどうなるか |
| テストケース | 重要な利用シナリオと失敗・復旧をどう検証するか |
| 画面モック | 利用者の目的、情報の優先順位、操作と復旧が妥当か |

同じ説明を複数成果物へ複製せず、必要な正本へリンクする。

## 二層の品質ゲート

### 機械ゲート

- 必須ID、リンク、トレーサビリティ
- 要件と設計・テストの対応
- 未解決事項と根拠の明示
- 構造化データ・図・本文の整合

### 判断ゲート

- 案件固有の業務・ブランド・既存構造に合うか
- 重要な要件の深さがリスクに見合うか
- 代替案とトレードオフを検討したか
- 例外・失敗・復旧・権限が現実的か
- 読者が短時間で結論、未決事項、次の判断へ到達できるか

判断ゲートは件数だけで自動合格にしない。生成担当と異なる担当者が根拠を読んで判定する。

次の状態は、機械ゲートを通過しても不合格とする。

- 本文がサマリ相当で、詳細が監査付録にしかない
- 同じ結論がサマリ・本文・監査付録へ長文で複製されている
- 低リスク項目も高リスク項目も同じ分量で並ぶ
- テンプレート見出しを埋めた順序のままで、読者の判断順に再編集されていない
