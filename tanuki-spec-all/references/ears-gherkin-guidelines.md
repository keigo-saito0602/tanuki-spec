# EARS × Gherkin 記述ガイドライン（受入試験の振る舞いを崩さない規範）

AIが受入試験のGherkinを書くとき、Thenが曖昧・UI操作の羅列・1シナリオに複数振る舞い・プレースホルダ、に崩れやすい。
このファイルはその崩れを防ぐ規範。②穴埋め生成で受入試験(AC)の `scenario` を書く前に必ず読む。

## 1. 要求はEARSで書く（要求層）

要件・受け入れ条件は次の5パターンのいずれかで書く。

| パターン | ひな型 | 例 |
| --- | --- | --- |
| 常時 | システムは、常に〜する | システムは、常に金額を税込で表示する |
| イベント駆動 | 〜のとき、システムは〜する | 予約が確定したとき、システムは確定通知を送る |
| 状態駆動 | 〜の間、システムは〜する | 定員に達している間、システムは予約ボタンを無効にする |
| 異常系 | もし〜なら、システムは〜する | もし残席が0なら、システムは満席エラーを表示する |
| オプション | 〜が有効な場合、システムは〜する | 招待コードが有効な場合、システムは特別価格を適用する |

## 2. 具体はGherkinで書く（シナリオ層）

EARSの1要求に対し、正常系・異常系・境界値の具体例を Given/When/Then で示す。

- **1シナリオ＝1振る舞い**。When は原則1つ。複数必要なら分割する。
- **Given＝前提状態**（操作ではない）。「〜済みである」「〜がある」。
- **When＝利用者の操作・イベント**を1つ。
- **Then＝観測可能な結果**。「表示される」「作成される」「通知が届く」。内部実装・画面座標を書かない。
- **宣言的に書く**。UI手順（座標クリックの羅列）にしない。
- **プレースホルダ禁止**。`<...>`・TODO・「適切に」「等」を残さない。
- 2件目以降の Given/When/Then は `And` で連ねる（レンダラが自動付与）。

## 3. データ違いは Scenario Outline

同じ振る舞いを入力データ違いで検証するときだけ `examples` を使う。
異なる振る舞いを `examples` に詰め込まない。

## 4. トレーサビリティ

各 `scenario` に対象US・要件をリンクする。レンダラがタグ（`@AC-xxx @US-xxx @要件ID`）を `.feature` に付与し、E2E結果を要件まで追跡できるようにする。
